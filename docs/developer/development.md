# Development Guide

This guide states the current behavior of the workspace browser plugin, the boundaries between its subsystems, the configuration and protocol surfaces it exposes, the commands that build and package it, and the checks that verify a release. The [repository instructions](../../AGENTS.md) state the rules that govern repository work; this guide states the implementation those rules apply to.

## Compatibility and Status

The implementation targets DSH Web and the main DSH Desktop window. The `engines.dsh` range in `package.json` declares both the oldest DSH release the current code is known to run on and the ceiling that DSH enforces. DSH evaluates an own `engines.dsh` range as the only requirement and includes prereleases, so both bounds matter: the lower bound keeps the plugin off an untested older release, and the upper bound makes DSH refuse a later release that this code has not been reviewed against. Read the accepted range from the manifest rather than from this guide, and move either bound only after re-verifying every surface listed here on the target release.

Web is local by default; administrators can opt in to a trusted remote Web origin. The Docker engine and registered workspace remain local to the DSH Host, not the remote viewer. The supported daemon platforms are native `linux/amd64` and `linux/arm64`; Windows requires Docker Desktop in Linux-container mode, and macOS requires local Docker Desktop on Intel or Apple Silicon. Daemon architecture aliases `x86_64` and `aarch64` normalize to `amd64` and `arm64`. The daemon determines the platform, not the Host process architecture or an emulation preference. Building the package does not verify runtime compatibility; complete the acceptance checks below before release. On Apple Silicon with local Docker Desktop, direct Host-to-runner verification has passed environment checks, native image building, sandboxed Chromium startup, Host-loopback HTTP navigation and inspection, and a clean restart using the same profile volume. Intel macOS runtime checks and the real Desktop and local Web UI acceptance checks remain pending. Chromium browsing supports HTTP(S) sites reachable from the DSH Host, including private networks, loopback, IPv6, and non-default ports. Host file transfer, access to the Docker host's own system clipboard, and audio forwarding are out of scope.

## Module Boundaries

| Area | Responsibility |
| --- | --- |
| `src/client/` | Native right-sidebar guide entry and tab, Session workspace lookup, noVNC client, clipboard bridge, and Browser Use settings and Session authorization switches. |
| `src/host/` | DSH admission, Session-to-workspace binding, runner lifecycle, and controlled egress. |
| `src/shared/` | Versioned Web contract and platform-independent validation. |
| `runner/` | Chromium, virtual display, and private automation, RFB, and proxy transport. |
| `test/` | Permanent Host and cross-module tests. |

The client requests browser lifecycle changes through the Host API; it has no direct Docker, runner-control, or Chrome DevTools Protocol endpoint. Web POSTs and all display WebSocket upgrades require a matching loopback Origin or an explicitly allowed Web origin, and DSH browser-owner admission in either case. Desktop forwards same-origin requests from its main window to its owned Host, removes the renderer Origin and Sec-Fetch-Site headers, and applies its own DSH owner authentication. The Host allows this originless path only for JSON POSTs marked with `x-dsh-plugin-workspace-browser-desktop: 1` that reach a loopback address and authority, with neither header present, and with the same DSH browser-owner admission. The marker is not a credential; the Host does not grant CORS access or accept the marker on a WebSocket upgrade.

The renderer opens the display socket through DSH Client Connection so Desktop uses its owned Host instead of the renderer's custom-scheme origin. The socket carries one short-lived, single-use ticket bound to the browser run, generation, workspace, and DSH Session before binary display traffic. The Host uses a separate text control message to tell the elected view to request framebuffer resizes. DSH treats its authenticated browser tabs as the same owner; workspaces are not distinct users or access-control roles, and resize ownership coordinates cooperating clients rather than authenticating them. Do not share the DSH browser-owner credentials with an untrusted party.

## Trusted Remote Web Access

In DSH Settings, open the Workspace Browser plugin settings. Under **Remote Web access**, enter one exact HTTP(S) origin per line and save. An origin is the scheme, the host, and the port when the port is not the default, for example `https://dsh.example.com`. Do not include paths or wildcards, and list only origins you administer. Use HTTPS for remote deployments.

The field updates `allowedWebOrigins` without editing a configuration file. The settings form exposes it as volatile: saving applies to subsequent HTTP requests and WebSocket handshakes without reloading the Host plugin or disconnecting existing display streams. To remove an origin, delete its line and save. Clearing the list restores the local-only default; removing your current origin prevents new plugin connections from that address. This setting admits the viewer's origin; it neither authenticates the viewer nor changes which sites Chromium can visit.

Serve DSH Web and the plugin's root-relative routes on the same public origin; arbitrary deployment path prefixes are unsupported. Keep the backend private. Configure the trusted reverse proxy to forward the original browser `Origin` and DSH owner cookie on both POSTs and display WebSocket upgrades, support WebSocket `Upgrade`, and strip any incoming `x-dsh-plugin-workspace-browser-desktop` header before forwarding. Do not synthesize an `Origin` or inject owner credentials. A loopback proxy connection does not prove the original client was local; stripping the marker prevents external requests from using the Desktop-only originless POST path. `Forwarded` and `X-Forwarded-*` headers are not proof of origin.

Before release, verify that a signed-in browser at the listed HTTPS origin can open a workspace and interact with the live display. In a test deployment, confirm both POST and display admission fail without the owner cookie or from an unlisted origin. Confirm the proxy strips the Desktop marker and that an originless external POST is refused. Repeat the local Web and Desktop checks with the list empty.

## Client Integration and UI Conventions

The Client registers browser commands through DSH's native context menu, using `contextMenu.button` and `contextMenus.register`. Switches appear inline, never in a menu. The plugin contributes profile settings to DSH's `plugins.bundle.config` slot and reads and writes them through `configForms`. External clients do not import DSH internal UI packages; the switches share a native HTML checkbox with switch semantics and an associated label.

The plugin adapts the Switch, Button, settings-card, tag, and spinner styles of the DSH release it targets to plugin-scoped classes and each control's native states, reusing DSH's dimensions, theme tokens, hover fencing, focus ring, and motion preferences. Settings rows are cards built from the `--dsw-alias-settings-card-fill` and `--dsw-alias-settings-card-stroke` tokens at the shared extra-large radius. Action buttons follow DSH's Button primitive with its primary, progress, and outline variants, its medium radius token, and a minimum target height that matches DSH. Check results are tag pills. The client does not depend on DSH's generated CSS class names and shows the native checkbox in forced-colors mode.

## Browser Lifecycle

Open or create a Session in a registered DSH workspace. An empty Session works without sending any messages; the home screen without a selected Session has no browser entry. Expand the native right sidebar, open its tool guide with **+** if needed, then select **Open workspace browser**. Chromium opens in a native sidebar tab alongside tools such as Files and Terminal. DSH owns docking and fullscreen behavior. The tab toolbar shows the separate **Share clipboard** and Session agent authorization switches plus the native **Chromium controls** menu button. There is no workspace picker: the Host resolves the workspace from the Session identifier submitted to `POST /dsh-plugin-workspace-browser/v2/view`, and unknown or ambiguous membership is rejected. Update the Host, Web client, and runner image together when installing this bundle.

Sessions in the same workspace share one running Chromium instance and persistent profile; different workspaces share neither. In the Chromium sidebar tab, open the native **Chromium controls** menu. **Restart Chromium** replaces Chromium without deleting the profile, keeps the bound sidebar tabs open, and reconnects visible views when ready. Use **Try again** after a startup failure or **Reconnect** after a display-only failure. **Close Chromium**, Chromium exit, or Host retirement ends that browser run and removes its bound Chromium sidebar tabs, including hidden ones. These events do not end DSH conversations or close other sidebar tools.

A hidden or closed tab releases its display connection. A hidden tab remains bound to its browser run and checks its lifecycle without holding a runner seat. Returning to a visible tab rejoins that run with a new one-time ticket; losing only the display connection does not terminate the run. Reopening the browser explicitly after retirement starts or joins a new run. `POST /dsh-plugin-workspace-browser/v2/browser/status` reports the bound run's state, and the `/browser/restart` and `/browser/close` requests include the generation to reject stale controls.

The native sidebar tab title follows the active Chromium window on the workspace display, including in-page title changes and switches between tabs or windows. After advertising readiness, the runner polls the display's foreground window name through `xdotool` on the private X11 display; this reads window properties only, so it needs neither page content nor Browser Use authorization. The Host keeps the latest name for the running generation and returns it as an optional `windowTitle` in the ready status; the existing status check interval updates the tab title without opening another connection. A missing, empty, retired, or non-current-generation title falls back to the localized browser name. To verify, rename the active page, switch between two differently titled windows, then restart Chromium: the sidebar should follow the foreground title without retaining the retired window's name.

The sidebar display fills its available area without a fixed aspect ratio. The first connected visible view requests Xtigervnc framebuffer resizes through noVNC; publishing a new size also changes the maximized Chromium window. Other views scale the shared framebuffer to fit, and the next connected view takes over resize when the current owner leaves. Xtigervnc runs without TCP listeners and uses a private Unix socket with mode `0600`; RFB-level clipboard exchange stays disabled. Text transfer uses the separate Session-authorized channel described below.

## Clipboard Authorization

The **Share clipboard** switch in the Chromium sidebar toolbar connects the viewer device's plain-text clipboard to the workspace display's X11 `CLIPBOARD` selection. It does not read the primary selection and does not reach the Docker host's clipboard. The Host stores the grant in memory per DSH Session and browser generation, independently of Browser Use: granting clipboard access never authorizes the agent tool, and revoking agent access leaves a clipboard grant intact. Other Sessions sharing that display need their own grant.

Web adds a second, independent requirement: the browser must allow clipboard writes for the DSH origin before remote text can be copied back automatically. This site permission is not a Session grant and never substitutes for one. Use HTTPS or loopback; the Clipboard API is unavailable in insecure remote contexts. Only plain text within the per-transfer byte limit defined by `MAX_CLIPBOARD_BYTES` in `src/shared/protocol.js` is accepted. Images and files are not transferred. Treat the grant as access to everything you copy while it is on, and note that text pasted into the shared browser may be visible to other Sessions.

Pasting into the display goes through the trusted, user-initiated paste event so no background clipboard read is needed: the client writes the text to the display first and only then sends one `Ctrl+V` chord. Remote text is copied back only while the view is visible and focused. A value that could not be delivered for lack of permission stays pending and is delivered once permission is granted; delivery never prompts. If automatic copying stays unavailable, use **Chromium controls → Transfer clipboard text** to read the current value or paste manually. Switching Session, hiding the tab, losing focus, revoking the grant, or a browser generation change discards pending transfers so stale text is never replayed.

To verify, use Web and Desktop to copy Chinese text, emoji, and multiple lines in both directions. With two Sessions in one workspace, grant only one and confirm the other cannot read or write clipboard data. Revoke from a second view of the granted Session and confirm transfers stop. Switch Sessions while a permission prompt is open, then reconnect; neither case should paste stale text. Deny the site clipboard permission and confirm the manual fallback, then grant it and confirm pending text arrives without another copy.

## Runner Isolation and Workspace Files

The Host starts one runner on demand per workspace, with a separate Chromium profile volume and display. Opening the browser exposes the entire registered workspace, not just a downloads folder: the local Docker engine bind-mounts it read/write at `/workspace`, Chromium's default download directory. Files selected for upload may come from this directory; downloads and edits persist independently of the browser profile. Use a dedicated workspace if the browser should not have access to other project files. The runner has no published ports or Docker socket. It runs with Docker networking disabled and requires an active loopback interface. Additional kernel interfaces are accepted only when administratively down, with no non-loopback addresses or IPv4 or IPv6 routes. Unreadable or malformed isolation metadata blocks startup. Chromium runs headfully with namespace and seccomp sandboxing. The runner refuses to advertise readiness if its isolation or display checks fail.

HTTP(S) traffic passes through a private broker that connects from the DSH Host and uses the Host's OS name resolution. `localhost` refers to the DSH Host, not to a remote viewer's machine or to the runner. The broker does not filter destinations: websites and authorized agents can send requests to HTTP(S) services on the Host and its private network. Keep the local engine and network routing under your control, protect sensitive services with authentication and network controls, and use trusted sites and Sessions. Chromium security rules, TLS validation, and the Host's DNS, routing, and firewall still apply. Never give the runner privileged mode, host networking, unrestricted seccomp, or the Chromium `--no-sandbox` flag.

## Linux Browser Account

On native Linux, use a local rootful Docker Engine without user namespace remapping. With an ordinary DSH Host account, Chromium uses the Host's effective UID and GID. A Linux root Host requires a local non-root account in the `rootBrowserAccount` plugin setting.

A dedicated system account is preferred: provision a locked, non-login account with a private primary group, using the vendor's account creation command, and do not reuse an account that runs other services. An ordinary non-root login account is also accepted, which is convenient when the workspace belongs to that user; the browser then acts with that account's own privileges, so keep it out of workspaces holding secrets that account must not read.

Rejected accounts are root, `nobody`, accounts whose UID is shared with another account, and accounts whose primary GID is another account's primary group. Supplementary groups and interactive shells are allowed because the runner always drops supplementary groups. Keep the numeric identity reserved while any files or ACL grants reference it. Chromium uses that UID and GID; it does not run as root or fall back to the image's default UID. In the plugin's **Environment** settings, select **Check environment** to verify the account.

The **Linux browser account** settings card appears only when the Host answers `POST /dsh-plugin-workspace-browser/v2/environment/platform` with `root: true`; it is independent of whether a value was stored, so the account can be entered the first time. That probe is read-only and runs no Docker command. The setting is volatile: saving it applies to the next browser launch and does not restart the Host plugin, while an already running Chromium keeps the identity it started with. The card rejects a name that cannot be a local account instead of writing it. Without a suitable account the browser cannot start. Do not use recursive `chown` or make the workspace world-writable.

On Windows and macOS, Docker Desktop must be allowed to share the workspace with the Linux VM. Remote engines are unsupported because bind sources are resolved by the daemon, not the Docker client.

When the runner reports insufficient directory permissions, the signed-in DSH browser owner can review the registered directory, service account, and numeric UID in the sidebar, then cancel or grant access and retry. No terminal command is needed to grant access. The environment check is read-only; missing ACL utilities affect graphical grants, not directories already writable by Chromium. For graphical grants use a root-owned directory with trusted root-owned ancestors; a sticky temporary parent is supported for a root-owned child. Full filesystem mounts are eligible, including independently mounted project disks and nested full filesystem mounts. Subtree bind mounts, subvolume roots, and paths overlapping a visible alias source on the workspace's filesystem are not eligible. Aliases of hidden directories on an ancestor filesystem do not refer to the independently mounted workspace. System trees, hidden path components, home directories themselves, and sensitive plugin paths are not eligible; `/root/workspace` is explicitly supported. Only authorize a dedicated workspace: persistent write access allows creating, deleting, and renaming top-level entries, including entries owned by others. Never grant access to code or configuration that a privileged service will subsequently trust. This is not an append-only download facility. Authorization does not recurse, install a default ACL, or change permissions on existing file contents.

Changing the account does not revoke ACLs or transfer ownership of existing downloads. During migration, stop the old browser and audit access ACLs and numeric file ownership. Revoke only grants attributable to the previous setup. Do not recursively change ownership or remove permissions used by unrelated accounts. Clear service-specific grants and address file ownership before deleting or reusing the dedicated UID.

To verify, open a workspace as a non-root Linux account whose UID does not match a common desktop login account, download a file, and inspect its numeric owner with `stat`. Without `sudo`, edit, rename, and delete the download. Also test replacing an existing writable file, restarting the browser with an existing profile, and downloading to a Windows shared directory with spaces in its path. With a root Host, start with a disposable root-owned workspace that has no extended ACL. Use a traversable parent for this test and keep an unrelated host account that is not the dedicated account. Check that an unset account leads to environment diagnostics, that cancelling the prompt leaves the original ACL intact, and that confirming enables a top-level download owned by the dedicated UID. The unrelated account must still be unable to create, replace, or delete entries. Repeat the grant on an independently mounted project disk and a nested full filesystem mount; both must permit the download without relaxing the bind and subtree restrictions. Replace the directory or change its mount after preview and during the final account or workspace recheck; the grant must be rejected without changing any ACL. Reopening the authorized workspace should not prompt again. Save a bookmark, restart Chromium, and verify that the same profile opens with the bookmark intact. Repeat in a separate root-owned workspace with restrictive permissions and decline the prompt: it must not create a download there, change the workspace permissions, or silently save the file elsewhere. A missing or unshareable workspace must not silently redirect downloads to the container.

## Idle Retirement and Profile Volume

The runtime retires when no workspace view is connected for `idleTimeoutMinutes`. The schema in `src/host/index.js` bounds the accepted value, and `src/host/pool.js` defines its default. Set it to 0 to disable idle retirement; manual close and workspace removal still retire the runtime. Change this value in the plugin settings without restarting the browser. The next idle check uses the new limit and counts time already spent disconnected. A connected view keeps the runtime alive even without user input. Removing a workspace registration retires its runtime but does not delete its profile volume.

The Docker volume contains browsing data such as cookies and history; do not share or export it as a diagnostic. A new DSH workspace registration has a new identity, even when its path is reused. Keep `profileNamespace` stable, and set it to a distinct value for each DSH profile sharing the same Docker engine before opening a browser. Keep Chromium and the container base current by rebuilding the image when deploying updates.

Each profile volume has a fixed runner container name. Docker atomically grants that name to at most one runner, even across Host processes. The Host also refuses to start if an active container already mounts the volume, including a pre-upgrade runner with a random name. Stop all old plugin instances before upgrading; concurrently running old and new versions against the same volume, or mounting a managed volume manually, is unsupported. An attempt that does not own a container must never stop or replace it. If a container remains registered under the fixed name, investigate it before retrying; the plugin does not forcibly reclaim it.

On its first launch after an interrupted shutdown or upgrade, the runner clears only Chromium's three top-level singleton symlinks; it does not remove their targets or reset the profile. An unexpected entry type or filesystem error fails startup with a profile-recovery message. Profile contention, recovery, generic startup, and failed isolation checks are reported separately. To repair or upgrade an installation of this bundle without changing its volume namespace, stop the old plugin instances, install the complete new bundle, and check or build the matching Runner image as described below. Then reopen the same registered workspace with the same `profileNamespace`. Do not remove the volume or re-register the workspace.

## Browser Use Authorization

In **Plugins → Installed → dsh-plugin-workspace-browser → Agent access**, use **Allow agents to use the workspace browser**. Toggling saves immediately, with no separate Save button. The switch displays the confirmed value and cannot be activated while a write is pending. The DSH configuration form writes only the active profile's `agentEnabled` setting and rejects writes based on an outdated revision. That setting defaults to `true` and makes the plugin's own `dsh-plugin-workspace-browser` tool available for registration across all workspaces and Sessions the instance serves; it does not authorize any Session. Disabling it stops admission, revokes existing Session grants, and cancels in-flight tool calls without restarting Chromium or closing manual views. Re-enabling it does not restore revoked grants.

The Session authorization controls map known Host error codes to localized user messages. Unrecognized failures show a generic localized request-failure message. Raw Host diagnostic text and internal error codes are not displayed by these controls.

Only the agent integration waits for DSH's general `tools` registry. If another plugin already registered a tool named `dsh-plugin-workspace-browser`, clear the conflict and disable and re-enable this integration. Losing the registry revokes active grants and cancels in-flight tool calls without closing manual views. The plugin implements Browser Use in its own Host and Chromium runner, without DSH's built-in Browser Use or Computer Use. It does not expose raw CDP, scripts, shell commands, filesystem operations, or unrestricted pointer and keyboard automation to the model.

Access is off by default in each Session. In the Chromium sidebar toolbar, turn on **Allow agent browser access for this session** when the provider is active and Chromium is starting, restarting, or ready. A display connection is not required. An authorized tool call made before Chromium is ready fails with a retryable error; calls are not queued. Hidden views and display disconnects do not revoke access or delay normal idle retirement.

The grant is held in memory for this Session and browser generation. It covers all supported web tabs, including background tabs and signed-in sites, with no per-site or per-action approval. Other Sessions sharing the browser need their own grants. Turning the Session switch off, a startup failure, browser restart or retirement, loss of workspace membership, or provider shutdown clears the grant and cancels in-flight calls. An action already delivered to a page cannot be undone.

Use `list` to find tabs and `navigate` with a tab ID and an absolute HTTP(S) URL without embedded credentials, including from a blank or new tab. Non-default ports are allowed, and navigation uses the same Host network reachability as manual browsing. `inspect` returns bounded page text and document and element references for subsequent actions; stale references are rejected. Chromium internal pages are not inspectable. Page content is untrusted and may include sensitive information visible to the signed-in browser, including in private-network tabs.

## Upgrade from the Previous Name

DSH treats `@local/dsh-workspace-browser`, whose entry ID is `workspace-browser`, and `dsh-plugin-workspace-browser` as different installations. Before enabling the new bundle, record your custom settings, disable the old bundle in every affected DSH profile, and confirm that its old Chromium runners have stopped. Install the complete new bundle and reload local DSH Web or reopen the main Desktop window. Restore custom settings in the new plugin before opening Chromium, including `profileNamespace` and `agentEnabled` if previously changed. Build the new local Runner image as described below. `agentEnabled` defaults to `true` for the new plugin; if you left agent integration disabled in the old bundle, disable it again. Session grants do not carry over; explicitly grant access again in each Session that needs it.

The renamed bundle opens fresh Docker profile volumes. Existing cookies, bookmarks, and history in old volumes are not available to the new bundle, even with the same `profileNamespace`; the old volumes are neither migrated nor removed. Update integrations to the new tool name, API prefix, and Desktop marker. The previous tool name, routes, and marker are not aliases.

## Build and Verification Status

The developer runs environment setup and builds by default. Agent execution is permitted only under the installation and build exceptions in the [repository instructions](../../AGENTS.md). Maintainers need the Node.js version declared by `engines.node` in `package.json`, npm, a compatible DSH installation, and a native `linux/amd64` or `linux/arm64` Docker daemon. Users need only the complete, trusted bundle and a running, compatible local Docker engine accessible to DSH. Windows uses Docker Desktop in Linux container mode.

On macOS, the default CLI selection checks `/usr/local/bin/docker`, `$HOME/.docker/bin/docker`, and `/Applications/Docker.app/Contents/Resources/bin/docker` in that order and uses the first existing path. If none exists, the environment check reports the unavailable CLI. The socket selection prefers `$HOME/.docker/run/docker.sock` when it exists and otherwise uses `/var/run/docker.sock`. These defaults support only local Docker Desktop, not remote Docker engines. An explicit `dockerExecutable` overrides the CLI selection and must be an absolute path; it does not override the local engine restriction.

By default the Host uses the [bundled seccomp profile](../../src/host/chromium-seccomp.json), based on [Moby's Apache-2.0 profile](https://github.com/moby/profiles/blob/seccomp/v0.1.0/seccomp/default.json) with [its license](../../src/host/chromium-seccomp.LICENSE.txt). The four Chromium-specific exceptions apply to both `amd64` and `arm64`: three argument-filtered `clone` rules permit only the required namespace flag combinations, and one `unshare` rule permits exactly the user namespace flag. These are not unrestricted syscall permissions. Other Docker restrictions and the mandatory Chromium namespace and seccomp sandbox checks remain in force. `seccompProfile` overrides this file only for administrators who have reviewed a local absolute path and its policy. A host kernel or security policy can still reject namespaces; do not disable the sandbox to work around it.

From the repository root:

```sh
npm install
npm test
npm run build
npm pack --dry-run
npm pack
```

The bundle includes the Runner's Dockerfile, `.dockerignore`, and every runtime file named by the Dockerfile's `COPY` instruction. The Docker context allowlist admits only those files. The package does not include a container image, an image manifest, or a previous release archive. `prepack` checks only that the two Client outputs and the Runner build inputs are nonempty files; it does not invoke Docker. When reviewing the package listing, confirm it contains those inputs and outputs, the Host and shared modules and seccomp policy and license, patch, locales, icon, and documentation.

For local development, `npm run build:runner` explicitly builds the image in your local Docker engine. It is not needed to package the plugin. The command uses the macOS CLI selection described above on macOS and resolves `docker` through `PATH` on other platforms. Both that command and the settings build query the local Docker daemon and normalize its Linux architecture through `src/shared/runner-image.js`. They build for the resulting native `linux/amd64` or `linux/arm64` platform. Runner launch uses the same platform, and image inspection rejects an image whose OS and architecture do not match it. Unsupported daemon platforms fail rather than falling back to emulation. Both build paths retain the existing `dsh-plugin-workspace-browser-runner:v<plugin-version>` tag using the version in the plugin package manifest; no architecture suffix is added. The tag replaces a SemVer `+` with `_`; the `dev.dsh.dsh-plugin-workspace-browser.plugin-version` image label keeps the full unchanged version. The `dev.dsh.dsh-plugin-workspace-browser.runner-protocol` label is an independent compatibility check. Both build paths pass `DSH_RUNNER_PROTOCOL` from the same constant used by image inspection; do not hardcode a second protocol number in the Dockerfile. Increment the plugin version when publishing a change to the Runner or its build inputs; do not republish different Runner inputs under a released version. The version label is applied after the version-independent Dockerfile steps so those layers can be reused across builds.

In each DSH profile you use, install and enable the generated bundle archive in the Plugin Manager. Reload the local Web page or reopen the main Desktop window as needed. Without opening a Session, go to **Plugins → Installed → dsh-plugin-workspace-browser → Environment** and select **Check environment**. The check shows which Runner version is required and whether it is ready; it never builds an image. Each check row states its own result, so a finished check adds no summary sentence and only an in-progress check is announced. If the exact image is missing or incompatible, use the build or rebuild action to build it from the installed bundle. This may take several minutes and requires network access to fetch uncached dependencies. A successful build is checked again, and its rows then report readiness.

After upgrading the plugin, repeat the check and build for the new version if needed. The old protocol-only tag is not migrated or used as a fallback. Different release tags can coexist; rolling back can reuse the matching older image if it still exists and passes inspection. Preserve the workspace registration and `profileNamespace` across upgrades and rollbacks to keep the same profile volume. The plugin does not migrate or downgrade the profile format itself; if the Runner releases contain different Chromium versions, test the rollback on a disposable workspace first. Opening Chromium never builds an image. Building, updating, and disabling the plugin do not delete images, build caches, or profile volumes.

Once the image is ready, open a Session in a registered workspace, expand the right sidebar, and choose **+ → Open workspace browser**. This is distinct from DSH's built-in Browser tool.

To verify the Runner's bundled fallback fonts after rebuilding the image, stop the old workspace browser and reopen it without removing its profile volume. Paste a data URL that renders English, Simplified Chinese, Traditional Chinese, Japanese kana, Korean, Arabic, Hindi, Thai, and an emoji into Chromium's address bar. Each sample should render without missing-glyph boxes. The test page must not use downloadable fonts.

Do not run a replacement DSH Web server or edit the profile's persistence files directly. For a runtime failure, report the first failing stage, HTTP status and error code if available, host platform, and Docker engine version. The stages are the tab, `/view`, the display handshake, and an established display. Do not include tickets, cookies, request payloads, or browsing data.

Use a test Docker engine without the required release tag for the missing-image case; do not remove images or volumes from the user's engine to create this condition.

### macOS Acceptance Checks

Run this checklist separately on Intel and Apple Silicon with local Docker Desktop. Record the macOS, DSH, and Docker versions, daemon architecture, and the result of each check. These are required verification steps, not a record of completed tests.

1. Check environment from the installed plugin. Confirm the CLI is selected from the documented path order, including a user-local CLI when the earlier path is absent. Confirm an absolute `dockerExecutable` override is honored and a relative path is rejected. Verify the user socket is selected when present and the system socket is selected otherwise. Do not alter the user's Docker installation or remove sockets merely to create a test condition; use a controlled setup for fallback cases. Confirm remote engines are rejected.
2. Confirm the daemon reports Linux and its native architecture: `amd64` or the `x86_64` alias on Intel, and `arm64` or the `aarch64` alias on Apple Silicon. Verify normalization, build platform, image OS and architecture checks, and runner launch all agree. Confirm the version tag and version and protocol label checks remain unchanged. An image for the other architecture must be rejected, not run under emulation. Use a disposable engine or controlled test fixtures for incompatible-image cases.
3. Build the matching image only through an explicitly authorized build operation. Confirm **Check environment** passes afterward without starting Chromium. Record this build and image result separately from runtime and UI results; neither a package build nor a runner image build proves Desktop compatibility.
4. In the actual main DSH Desktop window, open a Session and use the native right sidebar to open Chromium. Verify the live display, pointer and keyboard input, navigation, resizing, restart, and close. Repeat in the existing local Web application and record Web and Desktop results separately. Do not substitute a browser rendering of DSH Web, an HTTP probe, or automated tests for the real Desktop window check.
5. Use a shared workspace whose path contains spaces. Download a file, confirm it appears in that workspace, then restart Chromium and verify the persistent bookmark and profile. Verify required isolation checks pass with the bundled argument-filtered seccomp policy on each architecture. A namespace or seccomp failure must block readiness; do not use privileged mode, unrestricted seccomp, or `--no-sandbox` to obtain a passing result.
6. Complete the general UI and profile restart checks in this guide on each architecture. If the real Desktop window or either architecture is unavailable, report that verification as pending, independently of successful builds or other checks.

### Profile Restart Regression

1. Use a disposable registered workspace in a test DSH profile with a distinct `profileNamespace`. Open its browser and save a test bookmark. Close the browser tab, wait for the runner to stop after the idle interval, then reopen the browser and verify the bookmark remains.
2. While the browser is open, identify the disposable workspace's exact running container in Docker. Run `docker kill <test-container-id>` against only that container, and confirm the bound Chromium sidebar tabs close. Explicitly reopen Chromium in the same workspace, and verify that it reaches readiness and the bookmark remains. Do not remove the profile volume between launches.
3. Verify that a concurrent launch from a second Host targeting the same test workspace ID and namespace reports profile contention without interrupting the first runner. Confirm a different workspace can still start. Repeat the visible browser checks in both Desktop and local Web.
4. On a disposable runner, omit the required `no-new-privileges` option to verify that the runner emits `runner_isolation_failed` and never emits `ready`. Do not change the live plugin's configuration.
