# Development Guide

## Compatibility and Status

The implementation targets local DSH Web and the main DSH Desktop window in DSH 0.2.2-rc.5. Both use a loopback DSH Host and a local Linux/amd64 Docker engine. Windows requires Docker Desktop in Linux-container mode. Building the package does not verify runtime compatibility; complete the acceptance checks below on both surfaces before release. Browsing supports public IPv4 HTTP(S) sites on default ports only. Remote DSH Web, private and development sites, IPv6-only sites, host file transfer, host clipboard integration, and audio forwarding are out of scope.

The package declares the compatibility range `engines.dsh: ">=0.2.2-rc.3 <0.2.3-0"` and was verified against DSH 0.2.2-rc.5. DSH evaluates an own `engines.dsh` range as the only requirement and includes prereleases, so both bounds matter: the lower bound is the oldest release the current code is known to run on, and the upper bound makes DSH refuse an unreviewed 0.2.3 instead of loading it silently. The upgrade guides from rc.3 through rc.5 change no surface this plugin uses, so adapting to a new 0.2.2 prerelease is a manifest and verification change; re-verify the surfaces listed above against the target, then retest on both surfaces and move the upper bound only after a 0.2.3 review.

## Module Boundaries

| Area | Responsibility |
| --- | --- |
| `src/client/` | Native right-sidebar guide entry and tab, Session workspace lookup, noVNC client, and Browser Use settings and Session authorization switches. |
| `src/host/` | DSH admission, Session-to-workspace binding, runner lifecycle, and controlled egress. |
| `src/shared/` | Versioned Web contract and platform-independent validation. |
| `runner/` | Chromium, virtual display, and private automation, RFB, and proxy transport. |
| `test/` | Permanent Host and cross-module tests. |

The client requests browser lifecycle changes through the Host API; it has no direct Docker, runner-control, or Chrome DevTools Protocol endpoint. Web POSTs and all display WebSocket upgrades require a matching loopback Origin and DSH browser-owner admission. Desktop forwards same-origin requests from its main window to its owned Host, removes the renderer Origin and Sec-Fetch-Site headers, and applies its own DSH owner authentication. The Host allows this originless path only for JSON POSTs marked with `x-dsh-plugin-workspace-browser-desktop: 1` reaching a loopback address and authority, with neither header present and the same DSH browser-owner admission. The marker is not a credential; the Host does not grant CORS access or accept the marker on a WebSocket upgrade.

The renderer opens the display socket through DSH Client Connection so Desktop uses its owned Host instead of the renderer's custom-scheme origin. The socket carries one short-lived, single-use ticket bound to the browser run, generation, workspace, and DSH Session before binary display traffic. The Host uses a separate text control message to tell the elected view to request framebuffer resizes. DSH treats its authenticated browser tabs as the same owner; workspaces are not distinct users or access-control roles, and resize ownership coordinates cooperating clients rather than authenticating them. Never deploy this plugin behind a proxy or share the DSH browser-owner credentials with an untrusted party.

The Client registers browser commands through DSH's native context menu (`contextMenu.button` and `contextMenus.register`). Switches appear inline, never in a menu. The plugin contributes profile settings to DSH's `plugins.bundle.config` slot and reads and writes through `configForms`. External clients do not import DSH internal UI packages; the two switches share a native HTML checkbox with switch semantics and an associated label. The plugin adapts the Switch, Button, settings-card, tag, and spinner CSS shipped in DSH 0.2.2-rc.5 to plugin-scoped classes and each control's native states, reusing DSH's dimensions, theme tokens, hover fencing, focus ring, and motion preferences. Settings rows are cards built from `--dsw-alias-settings-card-fill`/`-stroke` at `--dsw-radius-xl`; action buttons follow DSH's Button primitive (primary, progress, and outline variants, `--dsw-radius-md`, 32px minimum height); check results are tag pills. It does not depend on DSH's generated CSS class names and shows the native checkbox in forced-colors mode.

## Browser Lifecycle

Open or create a Session in a registered DSH workspace. An empty Session works without sending any messages; the home screen without a selected Session has no browser entry. Expand the native right sidebar, open its tool guide with **+** if needed, then select **Open workspace browser**. Chromium opens in a native sidebar tab alongside tools such as Files and Terminal. DSH owns docking and fullscreen behavior. The tab toolbar shows a Session authorization switch and the native **Chromium controls** menu button. There is no workspace picker: the Host resolves the workspace from the Session identifier submitted to `POST /dsh-plugin-workspace-browser/v2/view`. Unknown or ambiguous membership is rejected. Update the Host, Web client, and runner image together when installing this bundle.

Sessions in the same workspace share one running Chromium instance and persistent profile; different workspaces share neither. In the Chromium sidebar tab, open the native **Chromium controls** menu. **Restart Chromium** replaces Chromium without deleting the profile, keeps the bound sidebar tabs open, and reconnects visible views when ready. Use **Try again** after a startup failure or **Reconnect** after a display-only failure. **Close Chromium**, Chromium exit, or Host retirement ends that browser run and removes its bound Chromium sidebar tabs, including hidden ones. These events do not end DSH conversations or close other sidebar tools.

A hidden or closed tab releases its display connection. A hidden tab remains bound to its browser run and checks its lifecycle without holding a runner seat. Returning to a visible tab rejoins that run with a new one-time ticket; losing only the display connection does not terminate the run. Reopening the browser explicitly after retirement starts or joins a new run. `POST /dsh-plugin-workspace-browser/v2/browser/status` reports the bound run's state, and the `/browser/restart` and `/browser/close` requests include the generation to reject stale controls.

The sidebar display fills its available area without a fixed aspect ratio. The first connected visible view requests Xtigervnc framebuffer resizes through noVNC; publishing a new size also changes the maximized Chromium window. Other views scale the shared framebuffer to fit, and the next connected view takes over resize when the current owner leaves. Xtigervnc runs without TCP listeners and uses a private Unix socket with mode `0600`; clipboard exchange remains disabled.

The Host starts one runner on demand per workspace, with a separate Chromium profile volume and display. Opening the browser exposes the entire registered workspace, not just a downloads folder: the local Docker engine bind-mounts it read/write at `/workspace`, Chromium's default download directory. Files selected for upload may come from this directory; downloads and edits persist independently of the browser profile. Use a dedicated workspace if the browser should not have access to other project files. The runner has no published ports or Docker socket. Chromium runs headfully with namespace and seccomp sandboxing. The runner refuses to advertise readiness if its isolation or display checks fail. Public HTTP(S) traffic passes through a private broker: the Host checks every A record and dials a validated numeric IPv4 address without resolving it a second time. The broker is not a content filter, and operators must keep the local engine and network routing under their control. Never give the runner privileged mode, host networking, unrestricted seccomp, or the Chromium `--no-sandbox` flag.

On native Linux, run DSH as the ordinary account that should own downloaded files and use a local rootful Docker Engine without user namespace remapping. Chromium uses the Host process's effective UID and GID; existing filesystem permissions still apply. Do not repair downloads with `sudo`, recursive `chown`, or permissive workspace modes. On Windows and macOS, Docker Desktop must be allowed to share the workspace with the Linux VM. Remote engines are unsupported because bind sources are resolved by the daemon, not the Docker client.

To verify, open a workspace as a non-root Linux account (preferably with a UID other than 1000), download a file, and inspect its numeric owner with `stat`. Without `sudo`, edit, rename and delete the download. Also test replacing an existing writable file, restarting the browser with an existing profile, and downloading to a Windows shared directory with spaces in its path. A missing or unshareable workspace must not silently redirect downloads to the container.

The runtime retires when no workspace view is connected for `idleTimeoutMinutes` (0–1440 whole minutes, default 2). Set it to 0 to disable idle retirement; manual close and workspace removal still retire the runtime. Change this value in the plugin settings without restarting the browser. The next idle check uses the new limit and counts time already spent disconnected. A connected view keeps the runtime alive even without user input. Removing a workspace registration retires its runtime but does not delete its profile volume. The Docker volume contains browsing data such as cookies and history; do not share or export it as a diagnostic. A new DSH workspace registration has a new identity, even when its path is reused. Keep `profileNamespace` stable, and set it to a distinct value for each DSH profile sharing the same Docker engine before opening a browser. Keep Chromium and the container base current by rebuilding the image when deploying updates.

Each profile volume has a fixed runner container name. Docker atomically grants that name to at most one runner, even across Host processes. The Host also refuses to start if an active container already mounts the volume, including a pre-upgrade runner with a random name. Stop all old plugin instances before upgrading; concurrently running old and new versions against the same volume or mounting a managed volume manually is unsupported. An attempt that does not own a container must never stop or replace it. If a container remains registered under the fixed name, investigate it before retrying; the plugin does not forcibly reclaim it.

On its first launch after an interrupted shutdown or upgrade, the runner clears only Chromium’s three top-level singleton symlinks; it does not remove their targets or reset the profile. An unexpected entry type or filesystem error fails startup with a profile-recovery message. Profile contention, recovery, generic startup, and failed isolation checks are reported separately. To repair or upgrade an installation of this bundle without changing its volume namespace, stop the old plugin instances, install the complete new bundle, and check or build the matching Runner image as described below. Then reopen the same registered workspace with the same `profileNamespace`. Do not remove the volume or re-register the workspace.

## Browser Use Authorization

In **Plugins → Installed → dsh-plugin-workspace-browser → Agent access**, use **Allow agents to use the workspace browser**. Toggling saves immediately, with no separate Save button. The switch displays the confirmed value and cannot be activated while a write is pending. The DSH configuration form writes only the active profile's `agentEnabled` setting and rejects writes based on an outdated revision. That setting defaults to `true` and makes the plugin's own `dsh-plugin-workspace-browser` tool available for registration across all workspaces and Sessions the instance serves; it does not authorize any Session. Disabling it stops admission, revokes existing Session grants, and cancels in-flight tool calls without restarting Chromium or closing manual views. Re-enabling it does not restore revoked grants.

Only the agent integration waits for DSH's general `tools` registry. If another plugin already registered a tool named `dsh-plugin-workspace-browser`, clear the conflict and disable and re-enable this integration. Losing the registry revokes active grants and cancels in-flight tool calls without closing manual views. The plugin implements Browser Use in its own Host and Chromium runner, without DSH's built-in Browser Use or Computer Use. It does not expose raw CDP, scripts, shell commands, filesystem operations, or unrestricted pointer/keyboard automation to the model.

Access is off by default in each Session. In the Chromium sidebar toolbar, turn on **Allow agent browser access for this session** when the provider is active and Chromium is starting, restarting, or ready. A display connection is not required. An authorized tool call made before Chromium is ready fails with a retryable error; calls are not queued. Hidden views and display disconnects do not revoke access or delay normal idle retirement.

The grant is held in memory for this Session and browser generation. It covers all supported web tabs, including background tabs and signed-in sites, with no per-site or per-action approval. Other Sessions sharing the browser need their own grants. Turning the Session switch off, a startup failure, browser restart or retirement, loss of workspace membership, or provider shutdown clears the grant and cancels in-flight calls. An action already delivered to a page cannot be undone.

Use `list` to find tabs and `navigate` with a tab ID and an absolute HTTP(S) URL, including from a blank or new tab. Cross-site navigation follows the browser's existing network policy. `inspect` returns bounded page text and document and element references for subsequent actions; stale references are rejected. Chromium internal pages are not inspectable. Page content is untrusted and may include sensitive information visible to the signed-in browser.

## Upgrade from the Previous Name

DSH treats `@local/dsh-workspace-browser` (entry ID `workspace-browser`) and `dsh-plugin-workspace-browser` as different installations. Before enabling the new bundle, record your custom settings, disable the old bundle in every affected DSH profile, and confirm that its old Chromium runners have stopped. Install the complete new bundle and reload local DSH Web or reopen the main Desktop window. Restore custom settings in the new plugin before opening Chromium, including `profileNamespace` and `agentEnabled` if previously changed. Build the new local Runner image as described below. `agentEnabled` defaults to `true` for the new plugin; if you left agent integration disabled in the old bundle, disable it again. Session grants do not carry over; explicitly grant access again in each Session that needs it.

The renamed bundle opens fresh Docker profile volumes. Existing cookies, bookmarks, and history in old volumes are not available to the new bundle, even with the same `profileNamespace`; the old volumes are neither migrated nor removed. Update integrations to the new tool name, API prefix, and Desktop marker. The previous tool name, routes, and marker are not aliases.

## Build and Verification Status

The developer, not the agent, runs environment setup and builds. See the [repository instructions](../../AGENTS.md). Maintainers need Node.js 22 or later, npm, DSH 0.2.2-rc.5, and a Linux/amd64 Docker engine. Users need only the complete, trusted bundle and a running, compatible local Docker engine accessible to DSH. Windows uses Docker Desktop in Linux container mode. Configure `dockerExecutable` only if the fixed platform default is unavailable.

By default the Host uses the [bundled seccomp profile](../../src/host/chromium-seccomp.json), based on [Moby's Apache-2.0 profile](https://github.com/moby/profiles/blob/seccomp/v0.1.0/seccomp/default.json) with [its license](../../src/host/chromium-seccomp.LICENSE.txt). The amd64 additions only permit `clone` with Chromium's required namespace flag combinations (user alone, PID alone, or user + PID + network) and `unshare` with exactly the user namespace flag. Other Docker restrictions and the mandatory Chromium sandbox checks remain in force. `seccompProfile` overrides this file only for administrators who have reviewed a local absolute path and its policy. A host kernel or security policy can still reject namespaces; do not disable the sandbox to work around it.

From the repository root:

```sh
npm install
npm test
npm run build
npm pack --dry-run
npm pack
```

The bundle includes the Runner's Dockerfile, `.dockerignore`, and the seven runtime files named by the Dockerfile's `COPY`. The Docker context allowlist admits only these nine files. The package does not include a container image, an image manifest, or a previous release archive. `prepack` checks only that the two Client outputs and the nine Runner build inputs are nonempty files; it does not invoke Docker. When reviewing the package listing, confirm it contains those inputs and outputs, the Host and shared modules and seccomp policy/license, patch, locales, icon, and documentation.

For local development, `npm run build:runner` explicitly builds the image in your local Docker engine. It is not needed to package the plugin. Both that command and the settings build use `linux/amd64` and tag the image `dsh-plugin-workspace-browser-runner:v<plugin-version>` using the version in the plugin package manifest. The tag replaces a SemVer `+` with `_`; the `dev.dsh.dsh-plugin-workspace-browser.plugin-version` image label keeps the full unchanged version. The `dev.dsh.dsh-plugin-workspace-browser.runner-protocol` label is an independent compatibility check. Both build paths pass `DSH_RUNNER_PROTOCOL` from the same constant used by image inspection; do not hardcode a second protocol number in the Dockerfile. Increment the plugin version when publishing a change to the Runner or its build inputs; do not republish different Runner inputs under a released version. The version label is applied after the version-independent Dockerfile steps so those layers can be reused across builds.

In each DSH profile you use, install and enable the generated bundle archive in the Plugin Manager. Reload the local Web page or reopen the main Desktop window as needed. Without opening a Session, go to **Plugins → Installed → dsh-plugin-workspace-browser → Environment check** and select **Check environment**. The check shows which Runner version is required and whether it is ready; it never builds an image. Each check row states its own result, so a finished check adds no summary sentence and only an in-progress check is announced. If the exact image is missing or incompatible, use the build or rebuild action to build it from the installed bundle. This may take several minutes and requires network access to fetch uncached dependencies. A successful build is checked again, and its rows then report readiness.

After upgrading the plugin, repeat the check and build for the new version if needed. The old protocol-only tag is not migrated or used as a fallback. Different release tags can coexist; rolling back can reuse the matching older image if it still exists and passes inspection. Preserve the workspace registration and `profileNamespace` across upgrades and rollbacks to keep the same profile volume. The plugin does not migrate or downgrade the profile format itself; if the Runner releases contain different Chromium versions, test the rollback on a disposable workspace first. Opening Chromium never builds an image. Building, updating, and disabling the plugin do not delete images, build caches, or profile volumes.

Once the image is ready, open a Session in a registered workspace, expand the right sidebar, and choose **+ → Open workspace browser**. This is distinct from DSH's built-in Browser tool.

To verify the Runner's bundled fallback fonts after rebuilding the image, stop the old workspace browser and reopen it without removing its profile volume. Paste `data:text/plain;charset=utf-8,English 简体中文 繁體中文 日本語かな 한글 العربية हिन्दी ไทย 😀` into Chromium's address bar. Each sample should render without missing-glyph boxes. This page uses no downloadable fonts. Then recheck the affected website.

Do not run a replacement DSH Web server or edit the profile's persistence files directly. For a runtime failure, report the first failing stage (tab, `/view`, display handshake, or established display), HTTP status and error code if available, host platform, and Docker engine version. Do not include tickets, cookies, request payloads, or browsing data.

After installation, run the following UI checks independently in the existing loopback Web application and in the main Desktop window. Use a test Docker engine without the required release tag for the missing-image case; do not remove images or volumes from the user's engine to create this condition.

Before opening a Session, open **Environment check**. Verify that opening settings does not run the check or build an image when no build has completed, that **Check environment** displays the required version without building, and that only the explicit build action starts Docker. Confirm that the build action stays visible for the whole build, showing a spinner with its label and `aria-busy` while disabled, including when the settings page is reopened during a build, and that it returns as an enabled retry after a failure. Confirm the post-build check leaves every row passed and no redundant summary sentence. Compare the environment rows, cards, and action buttons with the surrounding DSH settings and the Agent switch in light and dark themes, in both locales, at narrow widths, and using only the keyboard. Verify the spinner still reads as in progress under reduced motion and that cards, pills, and buttons keep visible borders and contrast in forced-colors mode. Verify that trying to open Chromium without the matching image fails without building. With two test plugin releases, build the first, then upgrade and verify it is not used by the new plugin. Build the second, confirm each release retains its own tag, then roll back and verify the old image and the same workspace bookmark are still usable.

### Profile restart regression

1. Use a disposable registered workspace in a test DSH profile with a distinct `profileNamespace`. Open its browser and save a test bookmark. Close the browser tab, wait for the runner to stop after the idle interval, then reopen the browser and verify the bookmark remains.
2. While the browser is open, identify the disposable workspace’s exact running container in Docker. Run `docker kill <test-container-id>` against only that container, and confirm the bound Chromium sidebar tabs close. Explicitly reopen Chromium in the same workspace, and verify that it reaches readiness and the bookmark remains. Do not remove the profile volume between launches.
3. Verify that a concurrent launch from a second Host targeting the same test workspace ID and namespace reports profile contention without interrupting the first runner. Confirm a different workspace can still start. Repeat the visible browser checks in both Desktop and local Web.
4. On a disposable runner, omit the required `no-new-privileges` option to verify that the runner emits `runner_isolation_failed` and never emits `ready`. Do not change the live plugin’s configuration.
